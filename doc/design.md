# 3D 扫雷 · 需求与游戏逻辑设计

文档状态：原型设计（对应 `prototypes/minecube/` 实现）
引擎：Godot 4.7.2 stable

## 一句话定义

把 2D 扫雷的格子换成方块，把平面邻域换成空间邻域，其余规则不变——用来验证"三维空间里的演绎推理是否成立"。

## 规则形式化

盘面是一个离散网格 `G = {0..W-1} × {0..H-1} × {0..D-1}`，每个格点一个单位立方体。

雷集 `M ⊂ G`，`|M| = m`。

邻域取切比雪夫距离 ≤ 1 的全部格点，共 26 个：

```
N(p) = { q ∈ G : 0 < ‖p − q‖∞ ≤ 1 }        |N(p)| ≤ 26
```

方块表面刻的数字：

```
c(p) = |N(p) ∩ M|
```

沿用 2D 的四条规则：

| 规则 | 形式 |
| --- | --- |
| 揭示 | 对 `p ∉ M`，把 `p` 置为已揭示；若 `c(p) = 0`，递归揭示 `N(p)` 中所有未揭示且非雷格 |
| 插旗 | 对未揭示格 `p` 切换旗标，不改变揭示状态，不消耗步数 |
| 失败 | 揭示到 `p ∈ M` |
| 胜利 | `∀p ∉ M`，`p` 均已揭示 |

首击安全：雷在首次揭示后才生成，候选集排除首击格的闭邻域。

```
M ⊂ G \ ({p0} ∪ N(p0))
```

若该集合容量不足 `m`，退化为 `M ⊂ G \ {p0}`。这一步保证首击格的数字恒为 0，第一次点击必然触发一次展开。

## 为什么 3D 不是 2D 加一维

规则可以逐条搬，但博弈结构会变。

| 指标 | 2D 9×9（12.3% 密度） | 3D 4³（12% 密度） |
| --- | --- | --- |
| 格数 | 81 | 64 |
| 邻接数 | 8 | 26 |
| 数字上限 | 8 | 26 |
| 单雷污染格数 | ≤8 | ≤26 |
| 空格占比 `(1−p)^k` | ≈0.35 | ≈0.033 |

按这个估算，三维的空格率只有二维的十分之一，看起来点不出连锁、"点一下开一片"的爽感会消失。实测把这个判断推翻了。每个配置跑 400 局随机首击（`tests/balance_probe.gd`）：

| 盘面 | 雷 | 密度 | 0 格占比 | 首击平均展开 |
| --- | --- | --- | --- | --- |
| 3³ | 3 | 11.1% | 29.1% | 72.7% |
| 4³ | 6 | 9.4% | 24.4% | 60.8% |
| 4³ | 9 | 14.1% | 15.0% | 48.4% |
| 5³ | 12 | 9.6% | 20.5% | 52.1% |
| 5³ | 16 | 12.8% | 13.3% | 38.0% |

结论和估算相反：三维的连锁展开不是太弱，而是太强。首击排除闭邻域之后，4³/6 雷平均一次点击就开掉六成非雷格，剩下的只是收尾。要回到 2D 那种"开局只开一小片"的节奏，密度得提到 14% 左右（4³ 配 9 雷），比 2D 的 12.3% 还高。

原因是那个公式只在内部格成立。三维盘面的边界格占了大头，角格只有 7 个邻格，`0.88^7 ≈ 0.41`，远高于按 26 邻域算出的 3.3%。把边界算进去，0 格的实际比例是估算的七八倍。

另一个结构差异：2D 里"角 3、边 5、心 8"是玩家内化的语法，三维里对应角 7、棱 11、面心 17、体心 26。数字的取值范围变了，但"结构位置决定数字上限"这条可读性设计仍然成立。

## 已确定的四个决定

**26 邻域。** 与 2D 的八邻域同构，保留上述结构语法。代价是数字跨度大、单格信息噪声高。

**实体外壳逐层剥离。** 方块不透明，挖开一层才看得到内层。视觉冲击强，代价是被埋住的数字只能靠记忆。

**4×4×4 起始盘。** 64 格 6 雷。`1`/`2`/`3` 键切换 3³/4³/5³。3³ 只用来验证操作与读数——相机旋转、拾取精度、剥离后的空间感知——不用来判断难度：27 格里首击平均就吃掉 72.7% 的非雷格。

**原型验证。** 不做菜单、音效、存档、难度曲线。判据是能不能玩通，以及玩家是否需要外部笔记。

## 遮挡与可玩性的冲突

"实体外壳剥离"和"能玩"之间存在一个硬冲突，必须在设计阶段解掉：

3³ 的体心方块被 26 个方块完全包住。它既看不见，也点不到。如果体心不是雷，玩家永远无法揭示它——胜利条件不可达。这不是难度问题，是死局。

半透明能解决可见性，但会毁掉"实体剥离"的体感；把揭示后的方块缩小到能看穿缝隙，又会让正对方向的射线始终被挡住。

解法是把**视觉阻挡**和**拾取阻挡**分开：

> 已揭示的方块保留网格与表面数字，但把碰撞体从拾取层移除。

射线只命中"未揭示或已插旗"的方块，于是点击一个已被剥离的位置会直接穿到它后面的内层方块。视觉上仍然是一层层挖进去的实心方块，操作上内层永远可达。玩家不需要理解这条规则，只会觉得"点进去"是自然的。

这条设计同时解决了另一个隐患：三维里总有方块被遮挡，如果拾取被遮挡物拦截，玩家会频繁遇到"点了没反应"。移除已揭示格的碰撞后，射线会自然地落到玩家真正想点的那个方块上。

## 数据结构

逻辑层共三个定长数组，索引 `i = x + W·(y + H·z)`：

| 数组 | 类型 | 含义 |
| --- | --- | --- |
| `mines[i]` | `PackedByteArray` | 是否布雷，0/1 |
| `counts[i]` | `PackedByteArray` | 邻域雷数，0–26 |
| `states[i]` | `PackedByteArray` | 0 隐藏 / 1 已揭示 / 2 已插旗 |

配套标量：`revealed_count`、`flag_count`、`hit_index`、`game_over`、`won`、`generated`。

选扁平数组而不是 `Dictionary<Vector3i, Cell>`：网格是稠密的，没有稀疏需求；索引可逆，`coord_of()` 一次整数除法就够；26 邻域遍历只做加法，不做哈希。

`counts` 在布雷后一次性预计算，`O(27 × 26)`。运行期揭示只读不写。

## 核心算法

**布雷。** 计算首击格闭邻域，从补集里洗牌取前 `m` 个。Fisher–Yates 原地洗牌，`O(n)`。

**计数。** 对每个非雷格遍历 26 个偏移，越界的跳过。3³ 是 702 次比较，5³ 是 3250 次，一次性开销，不需要优化。

**揭示与洪泛。** 显式栈的迭代式 DFS，不递归——5³ 的连通域能到 100+ 格，递归深度没有收益。展开时跳过已插旗格，尊重玩家意图。

**判定。** 每次揭示后比较 `revealed_count == total − m`。胜利时不再检查雷，因为踩雷路径已经先行返回。

## 交互映射

| 输入 | 行为 |
| --- | --- |
| 左键单击（位移 < 4px） | 揭示 |
| 左键拖拽 | 旋转环绕相机 |
| 右键单击 | 标记循环：未标记 → 旗 → 问号 → 未标记 |
| 右键拖拽 | 旋转环绕相机 |
| 滚轮 | 缩放 |
| 左右键同按（或中键） | 和弦 |
| `R` | 重开（沿用当前设置） |
| `Esc` | 关闭设置浮层 |
| 顶栏「重开」「设置」「关闭」 | 重开 / 打开设置 / 退出 |

和弦沿用微软扫雷的规则：在已揭示的数字格上，如果周围旗数恰好等于该数字，一次揭开所有未插旗的相邻未揭示格；旗数不等时什么都不发生。旗插错了照样会引爆——和弦的安全性完全由玩家的推理保证，游戏不做额外校验。三维里这一条比二维更关键：一个数字周围有 26 个邻格，逐个点一遍的成本太高。

和弦需要射线能命中已揭示的数字格，而揭示又需要射线穿过它们去打内层。所以碰撞层拆成两套：未揭示/已插旗在 `LAYER_SOLID`（揭示射线只认这一层，因此可以穿透数字格命中内部），数字格在 `LAYER_OPEN`（只给和弦和插旗用）。0 格没有碰撞。

阶数与雷数在设置浮层里选：3–9 阶，雷数 1 至 N³−1 颗，切换阶数时雷数自动落到 14% 密度的推荐值。浮层打开时暂停计时，同时挡住 3D 输入。

9 阶是 729 格、7362 个节点，全开状态下实测 59.7 FPS（垂直同步封顶），没有做额外的 LOD 或合批。

正计时从首次揭示那一刻起跑，胜利或踩雷时停住。清空后弹出完成面板，显示用时与盘面配置，可以直接再来一局。

点击与拖拽用 4px 位移阈值区分。取消右键拖拽的直觉：右键在三维里既想转相机又想插旗，唯一能同时满足的做法是按"动没动"分流。

## 视觉编码

| 状态 | 尺寸 | 颜色 | 面上的符号 | 碰撞 |
| --- | --- | --- | --- | --- |
| 隐藏 | 0.88 | 近白偏冷 | 无 | SOLID |
| 插旗 | 0.54 | 沙色 | 旗 | SOLID |
| 问号 | 0.54 | 灰蓝 | ? | SOLID |
| 已揭示，c > 0 | 0.54 | 深板岩 | 数字 | OPEN |
| 已揭示，c = 0 | 消失 | — | 无 | 无 |
| 雷（失败时） | 立体水雷 | 灰金属 | 无 | 无 |
| 踩中的雷 | 放大 1.18 | 红热叠加 | 无 | 无 |

方块是圆角立方体，按截面放样生成（`assets/build_cube.py` → `assets/cube_rounded.glb`，边长 1 的单位网格）。每层是一个圆角矩形（半宽 h、角半径 r）：做法是直接削角（`assets/build_cube.py` → `assets/cube_rounded.glb`）：立方体的八个顶点各被切掉一大块（沿棱 0.30、12 段），十二条棱保持原始直边、不做任何倒角。于是六个面是完整平面（四角被圆弧吃掉）、棱是一条清晰的直线、角是一块大圆弧面。

着色上必须把六个主面设为平直。切削面和平面并不相切，交界本来就是一道折边；整颗平滑的话，平面上的大多边形会被拉出斜纹——之前用 Bevel 两步倒角时踩过这个坑。现在按面法线是否为单位轴来区分：是主轴的面平直，其余平滑。

试过并放弃的方案：把面做成圆角矩形、棱也倒圆（截面放样）。那看起来像软垫，不是削角。两者的区别在棱——削角方案的棱是直的，放样方案的棱是一圈过渡带。

不用 Blender 的 Bevel 修饰器：两次倒角（顶点 + 棱）叠出来的拓扑里，封面是一个大多边形，平滑后法线渐变会显成斜纹；棱的倒角还会被重叠钳制卡住——角与棱抢的是同一条边长，两者之和不能超过 0.5，加角就必然减棱，且关掉钳制会让网格膨胀到 1.99 倍。放样全是四边形条带，两个半径独立可控。

视图按 0.88 / 0.66 两个尺寸缩放同一个共享网格，材质逐块覆盖，所以 729 格也不会产生 729 个网格资源。已揭示格 0.70、标签外移 0.018、字号 36。角半径变大后平面收窄，原来的 44 号字会顶到圆角上。

视图按 0.88 / 0.62 两个尺寸缩放同一个共享网格，材质逐块覆盖，所以 729 格也不会产生 729 个网格资源。

三种符号——数字、问号、旗——都印在方块表面，和数字同一套面选择逻辑：只在暴露面上出现，随方块一起转，斜到看不清时淡出。

旗子没有用 3D 立牌。系统字体里没有旗帜字形（U+2691 / U+2690 / U+1F6A9 在 PingFang 里都没有），所以旗面是运行时画的 96×96 纹理贴在面片上：深色旗杆 + 深边琥珀三角。这样旗和数字一样是"写在面上"的，不会插进上方方块。旗面片按需创建，只有真正被标记的格子才有，最多几十格。

问号直接用 ASCII `?`，和数字共用 Label3D。

标记不用红色。红色在扫雷里已经被"踩雷"占用了。沙色（旗）和灰蓝（问号）都不与深板岩数字格、近白隐藏格冲突。

雷是 Blender 生成的立体水雷（`assets/build_mine.py` → `assets/mine.glb`）：球体 + 赤道箍 + 14 根锥刺（六轴向 + 八对角），外径 0.80，装得进 0.88 的格子。踩中的那颗放大 18% 并叠一层红热材质，和其余雷拉开区别。材质金属度从 0.9 降到 0.45——场景里没有环境贴图，高金属度会直接渲染成黑块。

方块间隙 0.12，靠间隙和方向光投影读出体积。已揭示的数字方块缩到 0.54，缝隙宽度 0.46，足以看进内层；数字为 0 的方块直接消失，留下真正的空洞。

数字刻在所有暴露面上，不做朝向相机的 billboard——这是"立方体表面的数字"的字面实现，也让旋转相机时数字跟着方块一起转，空间关系不会漂移。代价是一个角块会同时看到 2–3 个相同的数。两条必须的处理：标签单面渲染（`double_sided = false`），否则透过缝隙会看到邻块的镜像字形；与视线夹角小于约 75° 的面淡出，否则掠射角上的「1」会被压成「7」的形状、读成别的数。

相机默认俯仰 34°。俯仰角在 `CameraRig` 里是"相机位于盘面上方"为正，取负会从下往上看，底面的数字全是倒的。

数字配色沿用扫雷传统色阶：1 浅蓝、2 浅绿、3 琥珀、4 橙、5 以上粉红。深色底上的对比度足够。

六个音，都来自 Freesound，来源、下载量、评分和许可证记在 `assets/sfx/CREDITS.md`。

| --- | --- | --- | --- |
| 揭示数字格 | Click_1 | 0.10s | 音高 ±6% 随机 |
| 洪泛展开（≥3 格） | Bubble_Pop | 0.18s | 按格数升调 0.92→1.34，同时提音量 |
| 插旗 / 撤旗 | Wooden Blocks | 0.24s | 撤旗降调用同一个音 |
| 和弦 | Bubble_Pop | 0.18s | 固定升到 1.28 |
| 踩雷 | Short Explosion | 1.46s | — |
| 胜利 | WinFantasia | 3.81s | — |
| 按钮 | Videogame Menu BUTTON CLICK | 0.18s | — |

两条取舍值得记：

揭示音只有 96 毫秒。揭示是最高频的操作，音效一旦超过 0.2 秒，连点就会糊成一片噪音。

洪泛不是单独一个音，而是同一个 pop 音按展开格数升调。这样"开一片"的规模和声音的亮度是对应的，不需要额外的素材。

插旗用的是两块木块相撞的实录（Neumann TLM 103 + API 调音台），下载量在这批里最低，但它是唯一一个录音说明精确到可以确定内容的命中——其余高下载量的"wood block"结果都是整段音乐。

六个音全部是 CC0，没有署名义务。`assets/sfx/CREDITS.md` 里记了每条素材的下载量、评分和选型理由。

`M` 键静音，状态显示在右上角的盘面信息里。

标记不要求先布雷：雷是在首击之后才放下去的，标记记在格子上，首击前插的旗会跟着保留。首击落在已插旗的格子上时按插旗处理，不会揭示。



## 状态机

```
        ┌──────────┐   首次点击   ┌──────────┐
        │  IDLE    │─────────────▶│ PLAYING  │
        │ 未布雷   │              │ 布雷完成 │
        └──────────┘              └────┬─────┘
                                       │
                        ┌──────────────┴──────────────┐
                        ▼                             ▼
                   ┌─────────┐                   ┌─────────┐
                   │  LOST   │                   │  WON    │
                   └─────────┘                   └─────────┘
```

`LOST` / `WON` 是终态，任何揭示与插旗请求都直接返回，只接受 `R` 重开。布雷时机绑定在首次点击而不是开局，这是首击安全的必要前提。

## 已知退化与风险

**体心信息泄漏。** 3³ 的体心格邻域覆盖全部 26 格，它的数字恒等于总雷数。只在奇数边长 ≤ 3 时出现（4³ 单格最多覆盖 26 < 64，不成立）。可以当成"总雷数读数"接受，但要意识到这是 3³ 特有的性质，不能拿它推断正常难度。

**3³ 不构成难度。** 27 格 3 雷，首击平均就开掉 72.7% 的非雷格，剩下的有效决策点不到十个。这一档只验证操作与读数。

**首击展开过强。** 4³/6 雷首击平均开掉 60.8%，5³/12 雷开掉 52.1%。四成到六成的盘面在第一次点击时就透明了。这是当前最需要调的一件事：把密度提到 14% 左右能把 4³ 的首击展开压到 48.4%。

**已揭示块的记忆负担。** 缩小的方块仍在原位，数字跟着方块转，理论上不需要记忆。但 5³ 有 125 个数字，同屏密度是否过高，只能靠实测。

**纯猜测不可避免。** 三维邻域的信息密度低于二维（单次揭示覆盖的候选比例更小），残局需要猜的概率会高于 2D。原型要记录的是猜测频次，而不是消灭它。

## 待验证的假设

> 如果玩家在 26 邻域的 3D 网格上逐层推理，能获得与 2D 同源的演绎快感——判据是首次游玩者在不借助外部笔记的情况下，5 分钟内清完 4³/6 雷的盘面，且纯猜测不超过 2 次。

最危险的假设不在规则层，在空间记忆：玩家能否在可自由旋转的立方体上维持"这个 3 指的是哪三个邻格"的稳定心理模型。这条只有在真人上手时才能证伪，代码正确性无法替代。
